**步骤 4：添加 SSH Keys**

进入 `root` 用户的编辑页面后，你会看到多个标签页（如 Profile、Access Tokens、SSH Keys 等）。

- 粘贴你的公钥（`cat ~/.ssh/id_rsa.pub` 的内容）

### 本地与远端分支分歧

> Git 不知道如何处理这种没有共同祖先的合并，因此 `git pull` 失败。

> 有时候 git push --force -u origin main 强制推送也不行哦！
>
> 因为 GitLab 上的 `main` 分支被设置为了 **Protected Branch（受保护分支）**，不允许强制推送（`--force`），这是为了防止意外丢失重要的历史提交。

**解决方案一：将本地内容合并到一个全新的初始提交中**

既然不能 `--force`，也不能直接 `pull`，我们需要一种方法来“桥接”这两个独立的分支。最安全的方法是：

1. **创建一个临时的合并提交**，将远程的初始内容和本地的现有内容合并起来。
2. **然后正常推送**。

```powershell
# 首先，确保你的本地工作区是干净的（没有未提交的修改）
# 如果有未跟踪或修改的文件，先提交 (git add .; git commit -m "Save local changes") 或暂时存储 (git stash)。
git status

# 获取远程仓库的信息，但不合并
# 这会下载远程仓库的数据到本地，但不会自动合并。
git fetch origin

# 将远程的 main 分支的初始提交作为父提交之一，创建一个新的合并提交
# 第一：查看一下当前状态；你会看到你本地的几个提交。
git log --oneline -5
# 第二：查看远程分支；你会看到远程的几个提交（它们和你本地的提交 ID 是不同的）。
git log --oneline -5 origin/main
# 第三：执行合并。告诉 Git 你想将 origin/main 合并进你当前的 main 分支。
git merge --allow-unrelated-histories origin/main
# 第四：检查合并结果；
git log --oneline -10

git push -u origin main
```



**解决方案二：丢弃本地所有历史，强制指向远程**：

```powershell
# 这条命令会将你本地的 main 分支指针移动到与远程 origin/main 完全相同的位置，并且丢弃所有本地独有的更改。
git reset --hard origin/main
```

对于一个正常、同步的仓库，标准操作流程是：

```powershell
# 在推送前，先拉取远程的最新更改；（如果本地有未提交的更改，git pull 会自动尝试合并，解决可能产生的合并冲突（如果有的话）。）
git pull origin main
# 提交你的更改。
git push origin main
```

### Gitlab 

#### SSH 免密认证

- **GitLab中的公钥**
  - **密钥对来源**：**Jenkins服务器生成**
  - **添加位置**：GitLab项目 → Settings → Repository → Deploy Keys
  - **用途**：让Jenkins服务器能够拉取GitLab的代码
- **Jenkins中的私钥**
  - **密钥对来源**：**Jenkins服务器生成**
  - **添加位置**：Jenkins → Manage Jenkins （凭据管理） → Credentials
  - **用途**：让Jenkins能够SSH连接到目标服务器（10.0.0.202/203）进行部署

```powershell
假设Gitlab服务器10.0.0.70	；	Jenkins服务器10.0.0.80
# 在Jenkins服务器中创建密钥对
ssh-keygen -t rsa -C "gitlab-jenkins@gitlab.com"
# 查看并复制私钥
cat /root/.ssh/id_rsa
# 查看并复制公钥
cat /root/.ssh/id_rsa.pub
# 在 GitLab 服务器上测试自身连接
ssh -T git@localhost
```



私钥在这个 **“凭据管理” (Manage Credentials)** 模块里添加；

然后点击下面那个带括号的 `(global)` （也可能显示为“全局”）**这几个字。这其实是个超链接，要点进去。

最后点击 **"adding some credentials"** 这个蓝色的超链接！

**填写表单（关键步骤）**：

- **类型 (Kind)**：必须在下拉菜单中选择 **SSH Username with private key**（带有私钥的 SSH 用户名）。
- **范围 (Scope)**：保持默认的全局 (Global) 即可。
- **ID**：自己起一个好记的英文名，比如 `gitlab-jenkins-ssh`。**这个 ID 非常重要**，以后你在配置 Jenkins 任务或者写 Pipeline 脚本时，就是通过这个 ID 来调用这把私钥的。
- **描述 (Description)**：写个中文备注，比如“用于拉取 GitLab 代码的私钥”。
- **Username**：填写 **`git`**（因为你是通过 `git@gitlab.duan.org` 去拉代码的，用户名就是 `git`）。
- **Private Key**：勾选 **Enter directly**（直接输入），然后会出现一个文本框。把你本地生成的 **私钥**（通常是 `~/.ssh/id_rsa` 里的内容，**注意不是 `.pub` 结尾的公钥**）完整地粘贴进去，记得要包含开头和结尾的 `-----BEGIN OPENSSH PRIVATE KEY-----` 和 `-----END OPENSSH PRIVATE KEY-----` 标记。





#### Webhook

##### 前提

⚠️ **避坑前置准备**：允许 GitLab 向内网发请求

出于安全考虑，GitLab 默认是**禁止** Webhook 向同一个内网（局域网）发送请求的。如果不改这个设置，一会测试时大概率会报错 `Url is blocked: Requests to the local network are not allowed`。

**你需要用管理员账号（root）登录 GitLab：**

1. 点击左上角的汉堡菜单，进入 **Admin Area (管理中心)**。
2. 在左侧导航栏找到 **Settings (设置)** -> **Network (网络)**。
3. 找到 **Outbound requests (出站请求)** 这一项，点击 Expand (展开)。
4. 勾选 **Allow requests to the local network from web hooks and services** (允许来自 web hook 和服务的本地网络请求)。
5. 点击 Save changes 保存。

###### **故障记录**

故障描述：

PostgreSQL 数据库底层存在某个卡死的事务或者表级死锁。不管是通过 Web 界面还是控制台，只要一执行针对该配置表的“Update 写入”操作，就会因为拿不到锁而一直等待，直到触发超时被系统强制掐断。于是涉及到写入操作都会导致 web 界面会崩溃。

过程和结果：

经过一系列的尝试和排错，发现卡死的程序行程了一个bug！最后**抛弃 GitLab 的界面和代码，直接用 SQL 语句把配置“硬写”进硬盘里！** 这是最极致、最暴力的绕过方案。

**第一步：直接暴力修改配置表**

咱们直接执行 UPDATE 语句，把“允许内网 Webhook”的开关强行拨到 `true`。复制并回车：

SQL

```
UPDATE application_settings SET allow_local_requests_from_web_hooks_and_services = true;
```

*(如果执行成功，屏幕上应该会返回类似 `UPDATE 1` 的字样，代表有 1 行数据被成功修改。)*

**第二步：验证是否修改成功**

为了确保万无一失，我们用 SELECT 语句查一下现在的状态：

SQL

```
SELECT allow_local_requests_from_web_hooks_and_services FROM application_settings;
```

*(如果返回的结果是 `t` (代表 true)，恭喜你，降维打击成功！)*

**第三步：退出并实战测试**

一路回车即可。这会生成两个文件：

3. **Credentials**：点下拉菜单，选择你之前配好的用来连接 GitLab 的凭据（注意别选成了 Harbor 的账号）。
4. **Branches to build**：默认是 `*/master`，如果你的 GitLab 默认分支叫 `main`，记得这里改成 `*/main`。

#### 第三步

> 构建触发器 (Build Triggers) —— 实现“提交即打包”

这里是自动化流水线的灵魂（打通 Webhook）：

1. 勾选 **Build when a change is pushed to GitLab. GitLab webhook URL: ...** 这一项。

2. **注意看这一行后面的 URL**（比如 `http://jenkins.duan.org:8080/project/2048-game`），**把这个地址复制下来**，等会儿要去 GitLab 里填。

3. 点击右下角的 **高级 (Advanced)**，往下滚动找到 **Secret token**，点击 **Generate** 按钮生成一串令牌代码。**把这串 Token 也复制下来**。

   *(注：配置完 Jenkins 后，你需要去 GitLab 的该项目 -> Settings -> Webhooks 里，把刚才复制的 URL 和 Token 填进去，选中 Push events 并保存。)*

#### 第四步

> 构建环境 (Environment) —— 暂时留空

我们这个项目比较简单，不需要特殊的环境注入，可以直接跳过这一步。

#### 第五步

1. 找到 **构建环境 (Build Environment)** 这一大项。
2. 勾选 **Use secret text(s) or file(s)**（使用秘密文本或文件）。
3. 在下方出现的 **Bindings (绑定)** 处，点击 **新增 (Add)**，选择 **Username and password (separated)**（分离的用户名和密码）。
4. 这时会出现三个框：
   - **Username Variable (用户名变量)**：填入 `HARBOR_USER`
   - **Password Variable (密码变量)**：填入 `HARBOR_PASS`

#### 第六步

> Build Steps (构建步骤) —— 核心打包脚本

这里是你要下达的具体指令：

1. 点击 **增加构建步骤 (Add build step)**，在弹出的菜单中选择 **执行 shell (Execute shell)**。
2. 在出现的那个大黑框里，把你之前学会的那些 Docker 命令写进去。为了让你体验大厂的规范，我帮你写了一个带版本号自动递增的标准 CI 脚本，直接复制粘贴进去即可：

#### 补充：

一个非常经典的 SSH 首次连接信任问题。

> 当你第一次通过 SSH（也就是 `git@...` 这种方式）连接一台新服务器时，系统会弹出一个提示问你：`The authenticity of host ... can't be established. Are you sure you want to continue connecting (yes/no)?` 只有输入 `yes` 后，机器才会把这个域名加入到已知主机列表（known_hosts）中。
>
> 由于 Jenkins 在后台拉取代码是一个自动化程序，**没有人工界面让它输入 `yes`**，而 Jenkins 默认开启了严格的主机密钥检查（strict checking），遇到不认识的域名直接就拒绝连接报错了。

### 📖 CI/CD 踩坑总结

> 遇到了一些 Docker 和 Jenkins 经典底层机制冲突。

**1. 坑一：Jenkins 的“假成功”骗局（掩耳盗铃）**

- **表现：** 哪怕中间 Docker 报错报得满天飞，只要最后一句 `echo` 成功了，Jenkins 就给你亮绿灯 `SUCCESS`。
- **破局：** 在脚本顶部加入 `set -e`。这是 CI 脚本的灵魂，遇到任何报错立刻切断，拒绝“报喜不报忧”。

**2. 坑二：子目录的“隐身术”（路径套娃）**

- **表现：** 报错 `unable to evaluate symlinks... no such file or directory`。其实 `Dockerfile` 已经推送到 GitLab 了，但 Jenkins 默认在根目录找，死活找不到。

- **破局：** GitHub/GitLab 下载的代码经常带一层外壳。用 `cd 2048-master` 命令，让 Jenkins 走进真正的工作车间再干活。

- ```powershell
  # 在 Dockerfile 中在开始处添加 cd 2048-master 这个进入下一级目录的指令；
  
  #!/bin/bash
  set -e
  cd 2048-master
  ```

  

**3. 坑三：权限重置的“无情铁门” (sock 套接字权限)**

- **表现：** 报错 `permission denied while trying to connect to the Docker daemon socket`。明明已经把 jenkins 加入了 docker 组，结果还是被拒。

- **破局：** 这是因为重启 Docker 服务 (`systemctl restart docker`) 会生成一个全新的 `docker.sock` 文件，把原本的权限洗掉了。最后我们用了“物理破门”手段：直接 `chmod 666 /var/run/docker.sock` 强行放行。

- ```powershell
  usermod -aG docker jenkins
  chmod 666 /var/run/docker.sock
  ```

**4. 坑四：Docker 的“HTTPS 强迫症”（443 端口撞墙）**

- **表现：** 报错 `connect: connection refused` 或 `http response to https client`。咱们的 Harbor 明明只有 80 端口，Docker 非要去撞 443 端口，就算加了 `:80` 也会触发协议冲突报错。

- **破局：** 修改了 Node 节点的 `/etc/docker/daemon.json`，把域名加入了 `insecure-registries` 白名单，告诉 Docker 这是自己人，允许降级走 HTTP。

- ```powershell
  cat /etc/docker/daemon.json
      {
        "registry-mirrors": ["https://docker.m.daocloud.io","https://docker.1panel.live","https://docker.1ms.run","https://docker.xuanyuan.me"],
        "insecure-registries": ["harbor.duan.org"]
       }
  ```

**5. 坑五：终极 BOSS —— 管道密码的“阅后即焚”连环案**

- **表现：** 这是最隐蔽的坑！用 `echo "密码" | docker login --password-stdin` 时，由于 Docker 第一次连 443 失败，回退去连 80 时，发现管道里的密码已经被“消费”完了，导致降级登录失败（而 root 手动敲密码却能成功）。

- **破局（邪修出场）：** 既然 `docker login` 命令本身有这个弱智 Bug，我们干脆弃用它。直接利用 Shell 脚本对账号密码进行 Base64 编码，**强行伪造出 `~/.docker/config.json` 认证文件**。只要有了这个“通行证”，Docker 守护进程推镜像时畅通无阻！

- ```powershell
  AUTH_TOKEN=$(printf "%s:%s" "${HARBOR_USER}" "${HARBOR_PASS}" | base64 | tr -d '\n')
  mkdir -p ~/.docker
  cat <<EOF > ~/.docker/config.json
  {
    "auths": {
      "harbor.duan.org": {
        "auth": "${AUTH_TOKEN}"
      }
    }
  }
  EOF
  
  # 与这个指令效果相同，类似于走小路到达目的地；
  docker login harbor.duan.org -u admin -p 123123
  ```

### K8s & Harbor

#### 第一步

> 在 **master1 (10.0.0.90)** 节点上执行以下命令，创建一个拉取镜像专用的 Secret：
>
> (执行完后，可以用 `kubectl get secret` 看一下，会多出一个叫 `harbor-auth` 的东西。)

```powershell
kubectl create secret docker-registry harbor-auth \
  --docker-server=harbor.duan.org \
  --docker-username=admin \
  --docker-password=123123 \
  -n default
```

#### 第二步

> Kubelet 使用 containerd 去拉取镜像，默认通过 HTTPS (443端口) 去连接镜像仓库。因为我们的 Harbor 没有配置证书，只有 HTTP (80端口)，所以会被拒绝连接。
>
> 需要在所有工作节点 的 containerd 配置文件中，告诉它 `harbor.duan.org` 是一个允许走 HTTP（跳过 TLS 验证）的仓库。

```powershell
# 编辑 containerd 配置文件
vi /etc/containerd/config.toml
    [plugins."io.containerd.grpc.v1.cri".registry.mirrors."harbor.duan.org"]
    endpoint = ["http://harbor.duan.org"]
    # 这里必须是 http ，不是 https
    [plugins."io.containerd.grpc.v1.cri".registry.configs."harbor.duan.org".tls]
    insecure_skip_verify = true
    # 这行配置的作用就是告诉 containerd：“对于 harbor.duan.org，跳过 HTTPS 验证，直接连！”
    
# 重启 containerd 让配置生效
systemctl restart containerd
```



#### 第三步

> 为了体现 K8s 的高可用特性，给游戏跑 **2 个副本**。同时，通过 `NodePort` 方式把游戏暴露到虚拟机的 `32048` 端口，方便你在 Windows 物理机的浏览器里直接玩。
>
> 在 **master1** 节点上，创建一个叫 `2048.yaml` 的文件：
>
> vi 2048.yaml

```powershell
# ==========================================
# 1. 部署控制器 (Deployment)
# 负责管理 Pod 的创建、副本数量和滚动更新
# ==========================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: game-2048
  labels:
    app: game-2048
spec:
  replicas: 2              # 启动 2 个副本，实现高可用
  selector:
    matchLabels:
      app: game-2048
  template:
    metadata:
      labels:
        app: game-2048
    spec:
      imagePullSecrets:    # 极其关键：调用咱们刚才创建的通行证去拉镜像
      - name: harbor-auth
      containers:
      - name: game-2048
        image: harbor.duan.org/game/2048:latest   # 你的 Harbor 镜像地址
        imagePullPolicy: Always                   # 总是拉取最新镜像
        ports:
        - containerPort: 80

---
# ==========================================
# 2. 服务暴露 (Service)
# 负责负载均衡，并将游戏端口暴露给外部浏览器
# ==========================================
apiVersion: v1
kind: Service
metadata:
  name: game-2048-svc
spec:
  type: NodePort           # 暴露为节点端口模式
  selector:
    app: game-2048         # 匹配上面 Deployment 的标签
  ports:
  - port: 80               # K8s 集群内部互相访问的端口
    targetPort: 80         # 容器内部 Nginx 的真实端口
    nodePort: 32048        # 物理机浏览器访问的端口 (范围必须在 30000-32767 之间)
```

在 master1 上执行手动部署：

> 执行完后，敲下 `kubectl get pod -o wide`。如果看到两个 `game-2048-xxx` 的 Pod 都是 Running 状态，那就说明前两步大功告成了！

```powershell
kubectl apply -f 2048.yaml
```

不多说了，启动，启动，启动！！！

http://10.0.0.91:32048
